## 2026-10-02 信息完整性复查

- 空的结束事件保留已接收的流式正文；结束事件只包含最后一条正文时，保留流中已有的前文。
- 分段保留空格、换行和缩进；流式预览的裁剪不作为最终正文。

## 第三轮 review：RPC 终态与并发交互

继续依据 Hermes 的单任务回复生命周期，检查实际安装的 Pi RPC 实现与 `AgentSessionEvent` 定义，发现以下问题并补充回归：

| 发现 | 修复与验证 |
| --- | --- |
| 第一个 `agent_end` 提前关闭回复，而 Pi 仍在重试、压缩或继续队列 | 对带 `willRetry` 字段的现代协议等待 `agent_settled`；没有该字段的旧协议继续按 `agent_end` 收尾。运行时验证重试与压缩期间任务归属不会提前释放 |
| 重试把失败尝试的文字带进最终成功回复 | 重试/overflow 压缩开始时移除失败当前段，保留此前成功段；测试最终只有恢复后的答案 |
| 当前 Pi 的 `compaction_start/end` 没有更新状态 | 兼容当前和旧名称，同时显示总结重试阶段 |
| 输入被扩展处理后没有模型事件，回复永远等待 | 成功 ACK 后，未开始模型的请求通过 `get_state` 确认空闲并收尾 |
| 扩展标为 `display: true` 的 custom 消息被过滤 | 保留显式可见正文，并在最终快照遗漏该消息时补回；隐藏 custom、思考和工具内部输出仍不作为公开正文 |
| 停止等待中的自动重试被显示为模型失败 | 以用户停止状态收尾，保留 🛑，无需额外 `agent_end` 才能解除等待 |
| `exit` 先于 stdout 排空，最后的答案/终态丢失 | 在进程 `close` 处理排空；末尾无换行的 RPC 行使用同一解析路径。测试在 exit 后注入尾部正文及终态，仍收到完整答案 |
| 多个提问共存时回复较早问题却答到了最新问题 | 按 Discord reply 引用的消息匹配问题；一个问题解决后，另一个未答则仍保持等待 |
| 完整附件已送达但占位消息编辑失败，引发附件重复发送 | 将后续失败作为占位清理失败，完整投递保持成功；测试只发送一次附件 |
| 模型已结束、最终回复仍在发送时，补充要求被收进永远不会提交的准备队列 | 区分准备、运行与投递阶段；投递期间的同用户补充合并启动下一轮，停止时明确取消。运行时测试检查确实多一次 prompt，且包含全部补充 |
| steer/排队已成功，但确认消息发送失败又告诉用户“未提交” | 将提交结果与确认消息投递分开；测试确认已接受的补充不会被误报为失败 |

真实隔离 Pi RPC smoke 还验证：input hook 处理输入、发送可见 custom 消息、返回成功 ACK 时，确实没有 agent_end/agent_settled，并且 get_state 返回空闲。此检查使用临时扩展和隔离 agent 目录，没有发起模型请求。构建、20 个测试套件及 diff 检查通过；真实 Discord 验证与此前记录的能力差距仍未改变。

本次参照 [Hermes 的 Discord adapter](https://github.com/NousResearch/hermes-agent/blob/main/plugins/platforms/discord/adapter.py) 的成品交互方式，重做网关的文字聊天与操作流程。首次读取为 2026-09-30，第二轮读取为 2026-10-02，重点是处理中/结束表情、原消息预览更新、结束后才发送溢出分段，以及提问和命令的收尾。

## 现在的行为

| 场景 | Discord 表现 |
| --- | --- |
| 收到任务 | 回复原用户消息，添加 👀，显示思考状态与已用时间 |
| 模型回复/工具执行 | 同一条回复显示文字预览与当前活动，更新合并并按顺序发送 |
| 等待确认或输入 | 回复显示“等待你的回答”；单独的提问提供按钮或填写弹窗 |
| 回答提问 | 原提问显示已选择/已提交并清除按钮；回复在原消息继续更新 |
| 提问超时/取消 | 原提问标记原因并清除按钮，RPC 收到取消回应，任务可继续收尾 |
| 完成 | 原回复替换为完整内容并移除停止按钮；👀 换为 ✅ |
| 失败 | 保留已生成的文字，显示错误；👀 换为 ❌ |
| 停止 | 使用停止按钮或 `/stop`；保留已有文字与会话，收尾显示 🛑 |
| 超长回复 | 生成期间只编辑预览；最终完整分段，超过 8 段优先发完整附件 |
| 部分分段发送失败 | 尝试完整附件；也失败时明示已发送段数，不重新发送已有前缀 |
| slash 命令 | 更新 Discord 已延迟的原响应，消除一直“思考中”的状态 |
| 模型/历史会话选择 | 操作结果更新回原选择器；旧列表保持自己的会话快照 |

默认会话对应频道自己的持久化 Pi 文件，网关重启后仍可恢复。`/new` 建立新历史，`/detach` 返回该频道的默认历史，`/continue`、`/resume` 的明确绑定仍优先。当前网关使用一个共享 Pi RPC worker：忙碌时，其他频道或其他用户收到忙碌提示；只有原频道的任务发起者可以补充要求。停止按钮属于任务发起者，管理员也可使用 `/stop` 停止任务。

输入回答不会被复制到提问的完成标记中。消息不会自动触发 `@everyone`、角色或回复通知。表情更新失败不会阻止正常回复；可以通过 `platforms.discord.reactions: false` 关闭表情。

## 修复的生命周期问题

- 等待最终结果的记录先于 RPC 写入建立，避免快速完成的结果被错当作孤立事件。
- 回复结束前等待正在发送的编辑完成，后续旧预览无法覆盖最终答案。
- 流式预览不发送溢出段；最终更新复用已发送的分段，避免重复。
- 提问在发起 REST 请求前登记，因此发送期间的停止/超时也能解除 Pi 等待。
- 按请求、频道、消息和用户验证按钮；陌生或过期请求不会回落到另一个待回答问题。
- RPC 子进程退出、模型失败、网关停止都会结清等待者与计时器；旧子进程的延迟退出不会清掉新 worker。
